# 3. УТВЕРЖДЁННЫЙ ТЕХНОЛОГИЧЕСКИЙ СТЕК

**Стек согласован заказчиком: Vite + обычные HTML/CSS/JavaScript. НЕ заменяй его на React, Next.js, TypeScript или Django по собственной инициативе.**

## Frontend

- Vite с шаблоном `vanilla`.
- Семантический HTML5, современный CSS3 и JavaScript (ES modules).
- Адаптивная вёрстка через Grid, Flexbox, `clamp()` и уместные container queries.
- Глобальные CSS-переменные для дизайн-токенов; организованные обычные CSS-файлы без CSS Modules.
- Анимации преимущественно на CSS; JavaScript только для настоящей интерактивности.
- `fetch()` для получения опубликованного меню и отправки заявки.
- Без тяжёлых UI-библиотек и без обязательных фреймворков.
- Локальная разработка через `npm run dev`, production build через `npm run build` (каталог `dist/`).

Визуальная точность должна быть **одинаковой** при любом стеке. Выбор простого JavaScript не является разрешением упрощать утверждённые макеты, композиции, адаптивность или анимации.

## Управление содержимым (Sanity CMS)

- Sanity CMS — источник опубликованных данных для меню кухни и барной карты.
- Отдельная Sanity Studio — защищённый интерфейс сотрудников для добавления, изменения, скрытия, сортировки и удаления позиций.
- Определи схемы документов для категории, блюда, напитка и настроек отображения; детали приведены в разделе 23.
- Публичный сайт получает только опубликованный разрешённый к показу контент.
- Доступ к редактированию осуществляется через авторизацию и права Sanity; **не создавай собственную систему учётных записей для гостей**.
- При разработке допустимы отдельные локальные тестовые данные; в production не выдавай их за реальный ассортимент.
- Не помещай API-токены с правами записи в браузер. Публичные чтения могут использовать безопасную публичную конфигурацию; приватные операции выполняются только через защищённую среду.

## Обработка заявок (минимальная серверная часть)

- Форма только **оставляет заявку на бронирование**: она не проверяет свободные столы и не подтверждает бронь автоматически.
- Серверная функция Netlify Functions (JavaScript, Node.js runtime) валидирует входные данные и отправляет сообщение в Telegram администратора через Telegram Bot API.
- Токен бота и идентификатор чата — только в серверных переменных окружения.
- Для этой согласованной версии НЕ нужны Django, Django REST Framework, PostgreSQL, Django Admin, собственная админка бронирований, таблица бронирований или сервис проверки доступности столов.
- Без работающего Telegram-получателя локальная верстка может запускаться, но отправка заявки должна честно сообщать о неготовой интеграции, а не имитировать успешную бронь.
- Требования по безопасности и персональным данным приведены в разделах 11 и 19.

## Публикация

- Предпочтительный вариант: Netlify для статического frontend и серверной функции (при доступности и соблюдении применимых требований).
- Sanity Studio размещается отдельно или способом, поддерживаемым Sanity; домен и права управления должны принадлежать заказчику.
- Не принимай решение о передаче персональных данных в зарубежные сервисы без проверки применимых требований и согласования с владельцем заведения; при необходимости серверный обработчик/хостинг заменяются на соответствующие требованиям, а дизайн и интерфейс сайта остаются неизменными.

## Организация проекта

Если репозиторий пустой, предложи минимальную структуру под Vite + vanilla JS с `src/`, `public/`, `netlify/functions/`, `sanity/` (отдельный Sanity Studio-проект или подпапка), `docs/`, `README.md` и `.env.example`.

Если проект уже существует, сначала изучи его. Не удаляй файлы и не переписывай архитектуру без необходимости. Не создавай микросервисы и сложную инфраструктуру ради сложности.

# 4. ДИЗАЙН-СИСТЕМА

Это один из важнейших разделов.

Весь сайт должен восприниматься как единая цельная композиция.

## 4.1. Цветовая палитра

Палитра основана на утверждённых изображениях.

Следующие цвета — стартовые ориентиры. Финальные оттенки необходимо сверить с референсами.

```css
:root {
  --color-bg-main: #100D0A;
  --color-bg-secondary: #17110D;
  --color-bg-elevated: #241811;

  --color-text-primary: #F3E8D6;
  --color-text-secondary: #C5B6A2;
  --color-text-muted: #988879;

  --color-accent: #E99824;
  --color-accent-hover: #F4AB3E;
  --color-accent-dark: #A75A14;

  --color-border: rgba(233, 152, 36, 0.28);
  --color-border-light: rgba(243, 232, 214, 0.32);

  --color-success: #789879;
  --color-error: #C9675E;
}
```

### Главный принцип

Основной фон — практически чёрный, но не нейтральный `#000000`.

Он должен иметь едва заметный тёплый коричневый подтон.

Янтарный цвет — акцентный, а не основной.

Кремовый — главный цвет текста.

## 4.2. Фоны и фактуры

Используй очень аккуратно:

- Ненавязчивую текстуру.
- Тёплую виньетку.
- Мягкие янтарные свечения по краям отдельных секций.
- Тёмные градиенты для улучшения читаемости.
- Полупрозрачные декоративные элементы.

Не нужно создавать ощущение грязного, зашумлённого интерфейса.

Избегай чрезмерной зернистости.

Разные секции могут отличаться по яркости, но переходы между ними должны быть плавными.

Особенно важно сохранить почти чёрный фон у утверждённых блоков «Преимущества», «Бронирование» и «Контакты».

## 4.3. Типографика

Нужны две согласованные гарнитуры.

### Заголовки

Выразительная антиква с поддержкой кириллицы.

Можно рассмотреть:

- Prata.
- Cormorant Garamond.
- Playfair Display.

Это кандидаты, а не разрешение произвольно менять типографику. Выбери тот шрифт, который ближе к утверждённым макетам.

### Основной текст

Современный удобочитаемый гротеск.

Возможные кандидаты:

- Manrope.
- Inter.
- Golos Text.

Не смешивай множество семейств.

### Иерархия

Ориентиры для десктопа:

| Элемент | Ориентир |
|---|---|
| Hero H1 | 64–86 px |
| Заголовки секций H2 | 54–76 px |
| Крупные акцентные слова | 80–110 px, если предусмотрены |
| Вводный текст | 20–24 px |
| Основной текст | 16–19 px |
| Текст кнопок | 14–17 px |
| Подписи | 12–14 px |

Все размеры должны адаптироваться через `clamp()`.

Крупные заголовки должны быть выразительными, но не ломать композицию.

Не используй произвольное увеличение текста ради визуального эффекта.

## 4.4. Контейнеры и отступы

Основной контейнер:

- Максимальная ширина примерно 1360–1480 px.
- На десктопе внутренние поля примерно 48–80 px.
- На планшетах 24–40 px.
- На смартфонах 16–24 px.

Основные секции должны иметь большие вертикальные отступы.

Ориентировочно:

- Десктоп: 100–160 px.
- Планшеты: 72–112 px.
- Мобильные устройства: 56–88 px.

Эти значения не обязательны буквально: сверяйся с референсами.

Главное — не сжимать сайт.

## 4.5. Кнопки

Два основных типа.

**Primary:**

- Тёплый янтарный или кремовый фон — в соответствии с конкретным макетом.
- Контрастный текст.
- Аккуратные скругления.
- Видимое состояние наведения.
- Плавные переходы.

**Secondary:**

- Прозрачный фон.
- Тонкая светлая или янтарная рамка.
- Кремовый или янтарный текст.

Сохраняй тип и цвет конкретной кнопки из её утверждённого макета.

## 4.6. Оранжевый росчерк

В нескольких заголовках используется характерный декоративный оранжевый росчерк.

Это повторяющийся мотив сайта.

Создай один переиспользуемый декоративный SVG-компонент `AccentStroke`.

Не используй скриншот заголовка целиком.

Не рисуй каждый росчерк совершенно по-разному.

Не делай его слишком ярким или толстым.

## 4.7. Иконки

Используй единый стиль:

- Тонкие линии.
- Янтарные акценты.
- Минимум декоративных деталей.
- Единая толщина линий.
- Единые правила размеров.

Допускается Lucide с необходимой настройкой.

Для блока преимуществ нужны четыре специальных значка в ромбовидных контурах, максимально близких к утверждённому изображению.

## 11.7. Логика бронирования

Это не просто декоративная форма.

Необходимо реализовать рабочий процесс отправки заявки.

**Важно: заявка не равна подтверждённому бронированию.**

Пользователь выбирает параметры, отправляет их, и заявка поступает персоналу.

После успешной отправки показывается:

«Заявка отправлена. Мы свяжемся с вами для подтверждения бронирования».

Не показывай сообщение «Стол забронирован», пока бронь не была подтверждена персоналом.

- Обязательное.

Дата:

Время:

- Доступные интервалы должны соответствовать подтверждённому графику работы.
- Не придумывай график работы, если его нет в конфигурации.

Количество гостей:

- Целое положительное число.
- Верхний предел задаётся конфигурацией.

Сообщения об ошибках должны быть понятными.

## 11.10. Согласованная серверная логика

Создай **небольшую серверную функцию** на JavaScript (например, `netlify/functions/booking.mjs`). Это обработчик отправки заявки, **не** система автоматического бронирования столов.

- Не создавай Django, Django REST Framework, PostgreSQL или Django Admin.
- Не разрабатывай статусную модель заказов/бронирований, список заявок на сайте и кабинет администратора бронирований.
- Обработчик принимает валидированные данные, формирует понятное уведомление и отправляет его администратору заведения через Telegram Bot API.
- Заказчик самостоятельно подтверждает столик гостю по телефону или согласованному каналу.
- Без базы данных заявка не хранится на сайте; честно опиши это ограничение и возможность резервного канала уведомления при необходимости.

## 11.11. API и формат заявки

Предпочтительный endpoint при размещении на Netlify:

```http
POST /.netlify/functions/booking
Content-Type: application/json
```

Тело запроса:

```json
{
  "customer_name": "Иван",
  "phone": "+79991234567",
  "reservation_date": "2026-12-01",
  "reservation_time": "19:00",
  "guests_count": 4
}
```

- Клиентская форма предварительно проверяет поля; сервер **повторно** валидирует все значения и нормализует телефон.
- Не принимай произвольные дополнительные поля, чрезмерные размеры тела запроса, потенциально вредоносный HTML или некорректные даты.
- Валидация даты и временных интервалов выполняется с учётом часового пояса Орла и подтверждённого графика работы, не придумывай график.
- Передавай в Telegram только необходимые данные: имя, телефон, дату, время, гостей. Экранируй специальные символы при разметке Telegram.
- При успешной отправке и положительном ответе Telegram возвращай безопасный JSON об успешной **передаче заявки**. Не возвращай `confirmed` и не сообщай о гарантированно свободном столе.
- При ошибке Telegram/сети возвращай код ошибки, показывай посетителю сообщение «Не удалось отправить заявку. Попробуйте ещё раз или позвоните нам» и не утверждай, что заявка принята.
- Не возвращай пользователю Telegram-токены, служебные идентификаторы или технические подробности.

## 11.12. Кому приходят заявки

- Уведомления должны поступать **заказчику или назначенному им администратору**, а не на личный аккаунт разработчика.
- Идентификатор целевого Telegram-чата и токен бота задаются только через защищённые серверные переменные окружения.
- Бот должен иметь права отправлять сообщения в выбранный чат; подтвердить интеграцию реальной тестовой заявкой после настройки.
- Не создавай на публичном сайте административную панель бронирований.
- По согласованию можно позднее добавить резервную отправку по email, но это не повод внедрять собственную базу данных сейчас.

## 11.13. Защита от злоупотреблений и надёжность

- Реализуй серверную валидацию, ограничения размера запроса и простую защиту от спама (например, honeypot плюс подходящий механизм rate limiting/anti-bot, совместимый с выбранным хостингом).
- Предусмотри защиту от двойного клика и явно повторяющихся отправок. Не обещай абсолютное исключение дублей без постоянного хранилища.
- Ошибки интеграции логируй без раскрытия номеров телефонов и токенов.
- Для локальной разработки допускается явно обозначенный тестовый режим, но в production нельзя симулировать отправку.
- При отсутствии настроенных Telegram-секретов серверная функция должна корректно возвращать ошибку, не «успех».

## 11.14. Персональные данные

Поскольку форма собирает имя и телефон, необходимо предусмотреть:

- Ссылку на политику обработки персональных данных и согласованный текст уведомления/согласия.
- Минимизацию передаваемых данных, HTTPS, отсутствие персональных данных в URL и аналитике.
- Предсказуемое поведение при ошибках и правила удаления/хранения заявок у выбранных получателей.
- Защиту от массовой отправки заявок.
- **Юридическую проверку передачи персональных данных в Telegram и выбора зарубежного хостинга/CMS**, в том числе требований к локализации и трансграничной передаче, до запуска на реальных клиентах. Не утверждай, что такая схема автоматически соответствует законодательству РФ.

Точный юридический текст и окончательные решения о сервисах/хранении должен предоставить или согласовать владелец заведения.

## 18.1. Разделение ответственности

- `index.html` — правильная семантическая разметка, блоки страницы, важный индексируемый текст.
- CSS-файлы — визуал, сетки, состояния, анимации, адаптивность.
- `navigation.js` — навигация, мобильное меню, якоря.
- `expandableMenu.js` — открытие/закрытие, фильтры, доступность двух меню.
- `kitchen.js` и `bar.js` — отображение данных своих категорий/позиций, без копирования общей логики.
- `services/sanity.js` — получение и безопасная нормализация опубликованного контента.
- `reservation.js` — клиентская валидация, состояния формы и `fetch()` запроса.
- `booking.mjs` — серверная валидация и отправка в Telegram, без клиентского доступа к токену.

## 18.2. Данные отдельно от разметки

Храни контакты, навигацию, настройки отображения и константы в отдельной конфигурации. Не дублируй телефон по разным модулям. Меню кухни и бара должны приходить из Sanity и не должны быть захардкожены в финальном коде.

Для локальной разработки разрешены **явно обозначенные** тестовые записи; не выводи их как реальную еду/напитки в production.

## 18.3. JavaScript

- Используй современные ES modules (`import`/`export`) без TypeScript и JSX.
- Функции должны быть небольшими и понятными, с логичным разделением ответственности.
- Обрабатывай ошибки сети и пустые ответы CMS.
- Предотвращай XSS: текст из CMS добавляй безопасным способом (например, `textContent`), не вставляй непроверенный пользовательский HTML через `innerHTML`.
- Используй `AbortController`/деактивацию запросов там, где это уместно.
- Включи ESLint при разумном объёме настройки; production build должен проходить без ошибок.

## 18.4. SEO для Vite

Vite с обычным JS по умолчанию не даёт серверный рендеринг. Сохраняй в исходном HTML ключевые описания гастропаба, заголовки, контакты и основной информационный контент, чтобы они не зависели от загрузки JavaScript.

Если полная номенклатура блюд/напитков должна индексироваться поисковиками, предусмотри отдельную возможность генерации статического HTML на этапе сборки по опубликованным данным Sanity и обновления сборки при изменениях в CMS. Это дополнительный механизм, не обязательный для первого визуального этапа. Нельзя утверждать, что любое клиентское `fetch()` автоматически гарантирует индексацию всего меню.

# 19. СЕРВЕРНАЯ ФУНКЦИЯ, CMS, БЕЗОПАСНОСТЬ И ПУБЛИКАЦИЯ

Полноценный кастомный backend не требуется: контентом управляет Sanity, бронирования обрабатываются одной небольшой серверной функцией.

## 19.1. Что обязательно

- Серверный обработчик POST-запроса бронирования на JavaScript (Netlify Functions или юридически/технически подходящий эквивалент).
- Строгая серверная валидация формы и безопасное формирование Telegram-уведомления.
- Отправка заявки в Telegram назначенному администратору с проверкой ответа API.
- Честное отображение результата отправки.
- Sanity Studio для редактирования опубликованного меню кухни и барной карты.
- Разграничение публичного чтения и административного редактирования.
- Никаких Django-проектов, миграций PostgreSQL и собственного административного кабинета заявок.

## 19.2. Безопасность

- Защита от спама и массовой отправки, подходящий rate limiting/anti-bot (при необходимости отдельное решение хостинга).
- Проверка входных данных на сервере; лимиты длины полей и размера JSON.
- Предсказуемые ответы об ошибках без раскрытия внутренней конфигурации.
- Корректный CORS, если frontend и API реально находятся на разных origins; не считай CORS и заголовок Origin полноценной защитой от ботов.
- HTTPS для публичного сайта и интерфейса редакторов.
- Отсутствие токенов Telegram, Sanity write-токенов и иных секретов в браузерном коде и Git.
- Минимизация логов персональных данных; никакой отправки телефонов в аналитические инструменты.
- Настройка прав сотрудников в Sanity; доступ к черновикам и публикации только у авторизованных пользователей.
- Проверка применимых правовых требований к Telegram и иностранным сервисам до боевого запуска.

## 19.3. Настройки окружения

Разделяй публичные настройки и секреты.

Пример `.env.example` (значения не заполнять реальными секретами):

```dotenv
# Допустимые публичные параметры; НЕ содержат прав на запись:
VITE_SANITY_PROJECT_ID=
VITE_SANITY_DATASET=

# Только серверная среда Netlify Functions:
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
```

При необходимости добавь версию API Sanity и безопасные build-only переменные. Не делай `VITE_`-переменные секретными: они доступны клиентскому коду. Для Sanity Studio используй её собственную конфигурацию/переменные и отдельное управление правами.

## 19.4. Локальный запуск

- Установка зависимостей проекта: `npm install`.
- Запуск frontend: `npm run dev`.
- Отдельный запуск Sanity Studio по её README.
- Для локального теста Netlify Functions при наличии Netlify CLI — `netlify dev`, или иной явно задокументированный тестовый способ.
- Отсутствие настроенного Telegram не должно препятствовать просмотру вёрстки, но реальная отправка заявки должна давать понятную ошибку, а не ложный успех.

## 19.5. Публикация и передача заказчику

- Подключить репозиторий GitHub к хостингу, убедиться, что `npm run build` создаёт `dist/`.
- Опубликовать фронтенд и обработчик заявок на подходящем хостинге, настроить переменные окружения только на сервере.
- Подключить домен заказчика и HTTPS.
- Настроить Sanity Studio, права сотрудникам и публичную выдачу только опубликованных записей.
- Проверить редактирование кухни и бара на тестовой согласованной позиции и фактическое изменение сайта после публикации данных.
- Проверить доставку заявки в Telegram заказчика.
- Если используется генерация HTML меню на сборке, настроить защищённый механизм перестройки сайта после публикации в Sanity; при клиентском чтении обновления обычно появляются после следующего получения данных с учётом кэширования.
- Передать владельцу доступы к домену, хостингу, репозиторию и CMS; не сохранять управление на личном аккаунте разработчика.
- Подготовить документацию: как добавить позицию, заменить цену/фото, скрыть товар, поменять N, найти ошибку заявки.
- Перед запуском с реальными персональными данными согласовать юридический текст и допустимость инфраструктуры для заведения в России.

Предусмотри в Sanity Studio удобную структуру для сотрудников заведения:

1. `FoodCategory` — название, slug/id, порядок, активность.

5. `MenuSettings` — начальное число видимых блюд и напитков (отдельные значения `N`), порядок показа и необязательные текстовые настройки меню.

## 23.2. Логика синхронизации

- Опубликованные данные из Sanity доступны frontend по безопасному публичному запросу или через механизм сборки.
- Изменение ассортимента и цены должно быть доступно сотруднику без редактирования кода.

- Не публикуй Sanity write-токены и не выдавай сотрудникам доступ к исходному коду для изменения меню.

Не заполняй неизвестные поля случайными значениями.

Запрещено использовать их в финальном сайте.

# 24. РЕАЛИЗАЦИЯ ФОРМЫ И ОШИБОК

Проверь следующие сценарии:

1. Пользователь пытается отправить пустую форму.
2. Пользователь вводит некорректный телефон.
3. Пользователь выбирает прошедшую дату.
4. Пользователь выбирает некорректное время.
5. Пользователь вводит некорректное количество гостей.
6. Пользователь нажимает отправку несколько раз.
7. Сервер недоступен.
8. Сервер возвращает ошибку валидации.
9. Сервер успешно принимает заявку.
10. Пользователь исправляет ошибку и повторяет отправку.
11. Telegram API недоступен или не возвращает подтверждение приёма сообщения.
12. Серверная функция запущена без необходимых секретов.
13. Срабатывает защита от спама/rate limiting.
14. Повторный клик не создаёт неконтролируемую серию заявок.

Форма должна вести себя предсказуемо.

Не показывай успех до фактического успешного ответа серверной функции **после** успешной передачи Telegram-уведомления. Сообщение об успехе означает только «заявка передана», не «стол забронирован».

- Использованы Vite + HTML/CSS/JavaScript без React/Next.js/TypeScript.

- Категории, состояния загрузки, доступность и ошибки работают корректно.

- Конфигурация вынесена из компонентов; секреты не находятся в клиентском коде.
